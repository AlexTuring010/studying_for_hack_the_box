M2 · Users Exist Concept 1

The Database & Migrations

🎯  Goal: understand where your users will actually live 🆕  Databases from zero — no prior DB experience assumed 🧩  Concept: tables, SQLite, and schema-as-code
Read me first

Milestone 1 is done — you have a working full-stack app. Milestone 2 makes it a real product: users who register and log in. But before a user can register, they need somewhere to live — and that's a database. You told me you've never set one up, so we start from zero: what it is, how it's wired in, and the one file that is your database.

The good news: you've been running a database this whole time without noticing. This lesson is mostly about understanding what's already there and verifying it — no new code today.

01Why a database (and not just a file)

So far your only "data" was hardcoded in a route — that ['name' => 'John Doe', …] array. It vanishes when the request ends. Real users must persist: survive restarts, be looked up by email at login, relate to their solves and scores. You could scribble them into a JSON file… and immediately hit walls. A database is purpose-built for exactly this:

You need to…A flat file strugglesA database gives you
Find one user by email, fastscan the whole fileindexed lookups
Handle many requests at oncecorruption / racessafe concurrent access, transactions
Guarantee rules (unique email, required fields)you police it by handconstraints & types enforced
Relate users ↔ solves ↔ challengestangled by handrelationships (foreign keys)
Bridge — from what you know

Think of a database table as a persistent, typed, indexed collection of records — like an array of structs that survives the process dying, that multiple clients can safely read and write at once, and that you can query by any field without writing the search loop yourself. It's the systems answer to "where does the state actually go."

02Tables, rows, and columns

A relational database organises data into tables. A table is like a strict spreadsheet: columns are the named, typed fields; rows are the individual records. Your users table looks roughly like this — and each person who registers becomes one new row:

the users table — columns across the top, rows down 
 id | name       | email             | password (hashed)     | created_at
----+------------+-------------------+-----------------------+------------
  1 | Alex       | alex@example.com  | $2y$12$Xk9…           | 2026-07-02
  2 | …          | …                 | …                     | …
 ↑                                    ↑
 primary key                          never stored in plain text (M2 security!)

The id column is the primary key — a unique handle for each row, auto-assigned. Note the password column already hints at a security lesson coming: it will hold a hash, never the real password. (Same principle as the flags we'll hash later — the server never stores the secret itself.)

03Your database is a single file (SQLite)

Here's why your "install a database" step felt like nothing: you're using SQLite. Most databases (PostgreSQL, MySQL) are server programs you install, start, and connect to over a port — real setup friction. SQLite is different: the entire database is one file. Yours is right here:

your whole database — one file 
builder/backend/database/database.sqlite     ← every table and row lives in here

No server, no port, no login — just a file Laravel reads and writes. That's ideal for learning and local dev. And Laravel knows to use it because of one line in your .env:

builder/backend/.env — how Laravel finds the DB 
DB_CONNECTION=sqlite
"But the plan said PostgreSQL/MySQL…"

It does — for production. We'll switch to a real database server at deploy time (M5). The beautiful part: because Laravel talks to the DB through an abstraction (migrations and Eloquent, next), switching is mostly changing these .env values — not rewriting your queries. Learn on the easy one now; swap the engine later for free. (One reason *.sqlite is in your .gitignore: each environment has its own database.)

04Migrations: your schema, as versioned code

So who created the users table inside that file? Not you, by hand — a migration did. A migration is a PHP file that describes a change to your database's structure ("create the users table with these columns"). Running them applies the changes:

the command that builds your tables 
php artisan migrate        # apply any migrations that haven't run yet

Your scaffold shipped three migrations, and laravel new already ran them for you (that's why database.sqlite isn't empty):

builder/backend/database/migrations/ 
0001_01_01_000000_create_users_table.php     ← the one that matters for M2
0001_01_01_000001_create_cache_table.php
0001_01_01_000002_create_jobs_table.php

Why bother with migration files instead of clicking tables into existence?

Migrations give you…Why it matters
RepeatableA teammate — or your production server — runs migrate and gets the identical schema. No "works on my machine."
VersionedSchema changes live in git, in order, next to the code that needs them. Your DB structure has a history.
ReversibleMade a mistake? php artisan migrate:rollback undoes the last batch.
The professional norm: schema-as-code

You never edit a production database by hand. You write a migration, commit it, and run it everywhere. Your DB's shape becomes reproducible, reviewable, and part of your project's history — the same discipline as everything else in git. (Your three migrations are already committed as part of the backend scaffold. ✓)

05A peek ahead: how Laravel talks to the data

Migrations build the structure (the empty table). Reading and writing the rows is a separate job, and Laravel gives you a clean tool for it: Eloquent, its ORM. Instead of writing raw SQL, you work with a model — a PHP class that maps to a table. Your scaffold already has one: app/Models/User.php maps to the users table.

php — the flavour of Eloquent (illustrative, next lesson) 
User::create([...]);              // insert a row
User::where('email', $e)->first(); // find a user by email
User::count();                    // how many rows

Don't worry about the details yet — that's next lesson, when you build registration and write the first real row. Today, just know: migrations shape the table; Eloquent fills and reads it.
