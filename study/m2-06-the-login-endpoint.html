M2 · Users Exist Concept 6

The Login Endpoint

🎯  Goal: POST /api/login that hands back a token 🔐  The other half of hashing — verifying, not storing 🧩  Concept: Hash::check, safe failure, tokens
Read me first

Registration stored a hashed password. Login is the mirror image: someone hands you an email and a password, and you have to decide "is this really them?" — without the server ever having kept the real password. That's four moves: validate the input, find the user, verify the password, and — on success — issue a token so they stay logged in.

Every piece you need — the query, Hash::check, the generic-error throw, createToken — is shown below as a concrete line. What's yours to write is the route: choosing the login validation rules, wiring the pieces together, and deciding what to return. I'll also teach a real security idea here — user enumeration — that most tutorials get wrong.

01Login is the other half of hashing

Back in M2-03 you deliberately made the password unreadable: the 'password' => 'hashed' cast stored a one-way bcrypt hash, and you can't turn a hash back into the password. That was the whole point — a leaked database gives up no passwords.

But now it creates a puzzle: at login the user types their password again, and you have nothing to compare it to, because you never stored the real one. The answer is the same trick, run forwards: hash what they just typed and compare the two hashes. If the fresh hash matches the stored hash, the passwords matched — and you learned that without ever holding the real password.

register vs login — same hashing, opposite directions 
register:  store  hash("hunter2")       →  $2y$12$Xk9…   (kept in the DB)
login:     is     hash(typed_password)  ==  the stored hash?   → yes / no
           the real password is never written down, on either trip
You won't hash by hand — Laravel does the compare

You will not write hash(...) and a string compare yourself — there's a subtlety (the salt, below) that makes a naive compare wrong. Laravel gives you one function, Hash::check, that does the "hash the input and compare correctly" step for you. Your job is to call it in the right place.

02The shape of a login handler

Before any code, hold the whole flow in your head. A login endpoint is these four steps, in order — and a fork: it either fails safely or hands back a token.

1
Validate the input
Same tool as register — $request->validate([...]) — but different rules (§3). Just enough to know an email and a password arrived.
2
Find the user by email
User::where('email', …)->first() — the row for that email, or null if there's no such account (§4).
3
Verify — or fail safely
No user, or Hash::check says the password is wrong → throw one generic error (§5). Both failures look identical from outside.
4
Issue a token & respond
Credentials good → mint a Sanctum token with createToken() and return it with the user (§6). That token is their "logged-in" pass.

The rest of this page is those four boxes, one at a time. You've already met the imports you'll need — two are new:

routes/api.php — imports (group these at the TOP) 
use App\Models\User;                            // already there
use Illuminate\Http\Request;                    // already there
use Illuminate\Support\Facades\Hash;            // NEW — for Hash::check()
use Illuminate\Validation\ValidationException;  // NEW — for the generic error

03Login validation ≠ registration validation

It's tempting to copy your register rules. Don't — login is a different question, so three of those rules are wrong here. Reason through each:

RuleRegisterLogin
email present & shaped like an email ✅ yes ✅ yes — you still need a well-formed email to look up
password present ✅ yes ✅ yes — you need something to check
unique:users on email ✅ yes (must be new) ❌ no — at login you want the email to already exist; unique would reject exactly the people allowed in
confirmed on password ✅ yes (typed twice) ❌ no — a login form has one password box, no password_confirmation
min:8 on password ✅ yes (setting a new one) ❌ no — you're checking against a stored hash, not enforcing a policy; length is irrelevant here

So the login rules boil down to: email — required, and email-shaped; password — required. That's the array you'll write. Notice validation here only proves the fields arrived and are the right type — it says nothing about whether the credentials are correct. That's the next two steps' job.

04Finding the user: where(…)->first()

You met this exact line in M2-05. It's the query-builder way to fetch one row by a column:

php — fetch the user for an email (textbook line) 
$user = User::where('email', $email)->first();
// → the matching User model, or  null  if no account has that email

The important choice is first() and not firstOrFail(). They differ only in the "nothing matched" case:

MethodNo match →Good for login?
->first() returns null — you decide what happens ✅ yes — lets you fold "no such email" into your own generic failure
->firstOrFail() throws → Laravel sends a 404 Not Found ❌ no — a 404 announces "that email doesn't exist" (see §5)

So use first(), keep the result (which may be null), and handle the null yourself in the next step — deliberately, not by letting the framework blurt out a 404.

05Verify the password — and fail safely

Now the heart of it. Hash::check takes the plain password the user typed and the stored hash, and returns a boolean:

php — verify a password (textbook line) 
Hash::check($plainPassword, $user->password);
//  true   if $plainPassword hashes to the stored hash
//  false  otherwise
//  arg order matters: PLAIN first, the STORED HASH second
Why not just hash it yourself and compare strings?

Because bcrypt mixes a random salt into every hash — so hashing "hunter2" twice gives you two different strings. A plain == between them would almost always say "no match," and nobody could ever log in. Hash::check reads the salt back out of the stored hash and recomputes correctly. Never compare hash strings by hand.

Why not Auth::attempt(), which tutorials love?

Auth::attempt() is for session logins — it checks the password and logs the user into a server-side session backed by a cookie. We're building a stateless token API (M2-04): no sessions, the client proves itself with a bearer token each request. So we do the two jobs explicitly — verify with Hash::check, then issue a token — and skip the session machinery entirely.

The security idea: don't leak which part was wrong

A login can fail two ways: (a) no account with that email, or (b) the email exists but the password is wrong. The naïve instinct is to say which — "no account found" vs "wrong password." Don't. That difference is a gift to an attacker:

If your messages differ……an attacker learns
"No account with that email" this email is not registered
"Wrong password" this email is registered — now they can target it (phishing, credential-stuffing, a focused password guess)

That probing is called user enumeration. You close it by making both failures identical — same status, same message. Laravel gives you a clean way to raise exactly that, matching the 422 validation errors your frontend already handles:

php — one generic credential error (textbook shape) 
use Illuminate\Validation\ValidationException;

throw ValidationException::withMessages([
    'email' => ['The provided credentials are incorrect.'],
]);
// Laravel renders this as a 422 with { "message": …, "errors": { "email": [ … ] } } —
// the SAME shape as $request->validate() failures your Vue form already reads

Putting the message under the email key just means your form shows it near the email field; the string itself is deliberately vague about why it failed.

Your move: combine the two failure cases into one

Here's the assembly I'm leaving to you (this is the learning): after the lookup, you have a $user that's either a model or null, and a plain password from the request. You want to throw that generic error when either there's no user or Hash::check returns false — and, crucially, to throw the same error in both cases. Write that one condition, throw the generic exception inside it, and let the code fall through to issuing the token (§6) only when both are fine. (Guarding with !$user first also means you never call Hash::check on null.)

Optional: the idiomatic auth.failed string

A hard-coded English message is perfectly fine. Laravel also ships a conventional translation key for this exact case, auth.failed ("These credentials do not match our records."). To use it as __('auth.failed') you first publish the language files with php artisan lang:publish — otherwise __('auth.failed') just returns the literal string "auth.failed", which isn't what you want. For now a plain string is the simpler choice; the security point (one identical message for both failures) is the same either way.

06Issue the token & respond

If the code reaches here, the credentials are good. Mint a token — the same call you ran in tinker back in M2-04, now living in the endpoint:

php — mint a Sanctum token (textbook line) 
$token = $user->createToken('auth-token')->plainTextToken;
// the RAW token string — Sanctum shows it to you ONCE here.
// The DB stores only a SHA-256 hash of it (same never-store-raw rule as passwords).

The string you pass ('auth-token') is just a human label for the token in the personal_access_tokens table — handy later for "revoke my phone's token." Now return the token together with the user, so the frontend has both:

  • What to return is your call — a shape like { token, user } is the norm. Returning the whole $user is safe: #[Hidden] strips the password on the way out (M2-05).
  • What the frontend does with it (next milestones): store the token, then send it on protected requests as Authorization: Bearer <token> — the bearer scheme from M2-04. That's how the user "stays logged in."
Fine for now: each login mints a fresh token

Log in three times and you'll create three valid tokens — that's expected and fine for the MVP (it's literally "three logged-in devices"). Revoking old tokens on login is a polish item for later, not something to solve today.

07Check yourself

Predict each before revealing it.

08Checkpoint — build POST /api/login

Add a login route to routes/api.php, next to register. Every line you need is shown above; you write the route, pick the validation rules, and wire the four steps together.

You're done when

Correct email + password returns a token (and a password-free user), and a wrong password and an unknown email return the identical generic 422 — and you can explain why Hash::check (not a string compare), why first() (not firstOrFail()), and why one message for both failures.

If something's off

Always the generic error, even with the right password? Check Hash::check arg order — plain password first, $user->password (the stored hash) second — and that you're not re-hashing the input. Getting a 404 for unknown emails? You used firstOrFail(); switch to first(). "Class 'Hash' / 'ValidationException' not found"? The new imports are missing or misspelled. Token is null / createToken undefined? The HasApiTokens trait isn't on User, or the personal_access_tokens table wasn't migrated (M2-04). Paste me the error and what the response body shows.

When login hands back a token on good credentials and one indistinguishable error on bad ones, come back. Then M2-07: we make that token do something — protect a route with the auth:sanctum middleware so only a valid Bearer token gets in, and read the current user with $request->user(). That's the loop closing: register → login → authenticated request.
