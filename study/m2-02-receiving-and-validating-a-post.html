M2 · Users Exist Concept 2

Receiving & Validating a POST

🎯  Goal: an endpoint that accepts registration data safely ✍️  You write real backend logic again today 🧩  Concept: POST + server-side validation
Read me first

Every endpoint you've built so far hands data out (a GET). Registration is the opposite: the client sends data in — a name, email, password — and your backend has to accept it. That's a POST. This lesson builds the receiving half: taking the data and validating it. Next lesson you'll hash the password and actually save the user.

You'll write this endpoint yourself. I'll teach POST and validation with generic examples and tell you exactly which rules registration needs — then you assemble it in routes/api.php.

01GET hands out; POST takes in

HTTP methods signal intent. You've only used GET (read something). Creating a user submits data, and the method for that is POST. The practical differences that matter today:

GETPOST
Intentread / fetchcreate / submit
Carries a body?no — data rides in the URLyes — the data travels in the request body
LaravelRoute::get(...)Route::post(...)
Trigger from a browser bar?yes (typing a URL is a GET)no — you need a tool (§5)

So your registration route is a Route::post, and the name/email/password arrive in the request body (as JSON). That last row is important: you can't test a POST by typing a URL — we'll deal with that in §5.

02Reading the incoming data: the Request

To read what the client sent, your handler asks for a Request object — Laravel hands it in if you type-hint it as a parameter. It represents the whole incoming HTTP request (body, headers, everything):

php — the shape of a handler that reads input (illustrative) 
use Illuminate\Http\Request;          // ← import it, like you import Route

Route::post('/example', function (Request $request) {
    $email = $request->input('email');   // read one field
    // ... $request->all() would give everything ...
});

Notice the use Illuminate\Http\Request; — same idea as the Route facade import you asked about: Request is a class, and use lets you write its short name. But you'll rarely poke at $request->input(...) field by field — because the very next step, validation, reads and checks everything at once.

03Validation: never trust the client

Rule of the trade: never trust input from the client. It can be missing fields, a junk email, a 2-character password, or crafted to attack you. Your server must check it before using it — this is a security boundary, not a nicety. Laravel makes it one call: $request->validate([...]).

php — validation on a DIFFERENT resource (illustrative, not your task) 
$validated = $request->validate([
    'title' => 'required|string|max:255',
    'count' => 'required|integer|min:0',
]);
// If any rule fails → Laravel stops here and returns a 422 with JSON errors.
// If all pass       → $validated holds the clean data, and your code continues.

Each field maps to a |-separated list of rules. The magic: on failure, validate() throws automatically — Laravel catches it and sends back a 422 Unprocessable Content with the errors as JSON. Your code below never runs. On success, it hands you back only the validated fields.

For registration, here are the rules you'll want — you write the actual call:

FieldRulesMeaning
namerequired · string · max:255must be present, text, not absurdly long
emailrequired · email · unique:userspresent, a real email shape, and not already in the users table
passwordrequired · string · min:8 · confirmedpresent, at least 8 chars, and matches a confirmation field
Two rules worth understanding

unique:users makes Laravel query your users table and reject the email if a row already has it — a database check, wired right into validation (see how the DB lesson pays off?). confirmed requires a second field named password_confirmation that must match password — the classic "type your password twice" safeguard. So your test request needs to send both password and password_confirmation.

04What a validation failure looks like

When validation fails, the caller gets a 422 and a predictable JSON body — the exact shape your Vue form will read later to show error messages:

a 422 response body (illustrative) 
{
  "message": "The email field is required. (and 1 more error)",
  "errors": {
    "email":    ["The email field is required."],
    "password": ["The password field must be at least 8 characters."]
  }
}
Why yours comes back as clean JSON

Remember that line in bootstrap/app.php: shouldRenderJsonWhen(… $request->is('api/*'))? That's what guarantees a validation error on an /api/* route renders as JSON (not an HTML error page or a redirect). It's already set up — another reason your endpoints live under /api.

05How to test a POST (you can't use the URL bar)

Typing a URL in the browser is a GET, so you need a way to send a body. Any of these work — pick one:

ToolGood becauseWatch out for
Browser console fetchyou already know it; no installruns cross-origin from the :5173 tab (CORS applies — yours allows it)
curl.exeno CORS at all (not a browser); scriptablein PowerShell, plain curl is an alias for something else — type curl.exe
REST client (Thunder Client, REST Client, Postman, Insomnia)the professional tool for APIs; saves requestsone-time install

The header that actually matters: Content-Type: application/json — without it, Laravel won't parse your JSON body, so every field reads as missing and you get baffling "required" errors (the #1 confusing failure here). Accept: application/json is good practice too, but on your /api/* routes you get JSON back either way (§4). The generic shape of a POST via fetch:

js — a POST from the console (illustrative testing scaffold) 
await fetch('http://localhost:8000/api/SOMETHING', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Accept': 'application/json' },
  body: JSON.stringify({ /* the fields you're sending */ }),
}).then(r => r.json())

07Checkpoint — validate a registration POST

Build the receiving half of registration. No database write yet — just take the data and validate it. You write the endpoint; the rules table in §3 is your spec.

You're done when

POST /api/register returns a 2xx for well-formed input and a 422 with JSON errors for bad input — and you can explain why we validate on the server (never trust the client) and what confirmed and unique:users do.

Testing gotchas

Always send Content-Type: application/json — without it Laravel won't parse your JSON body, so every field looks missing and you get bogus "required" errors (the #1 confusing failure here). Accept: application/json is good practice, though your /api/* routes return JSON regardless. In PowerShell, use curl.exe (plain curl is aliased). If the console fetch throws a CORS error, you're calling cross-origin from :5173 — that's allowed by your config, so re-check your URL/headers; or use curl.exe to sidestep the browser entirely.

When good input passes and bad input gets a clean 422, come back and tell me. Then the payoff: we hash that password (so the raw password is never stored — a real security practice, and the same idea as hashing flags later) and use the User model to write your first real row into the database.
