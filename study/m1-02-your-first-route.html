Your First Route

🎯  Goal: the browser gets a response you wrote ✍️  You write your first PHP today 🧩  Concept: routing + what a handler returns
Read me first

You finished M1-01 with a running backend, and you came back with a sharp question: "the page is HTML generated by a PHP process — but which code is that process? Is it the artisan file?" Good instinct. That question is the doorway to this whole concept, so we answer it first — precisely, using your files — and then you'll become that code by writing your first route.

Everything below points at real files inside builder/backend/. Open them alongside this page.

01Which code builds the page? (the two doors)

The short answer: no — it is not the artisan file. Your Laravel app has two front doors, and the artisan file is the other one.

Open these two files in builder/backend/ and look at the call near the bottom that does the actual work. They are almost identical twins — they even boot the same framework — until that one call, which is the whole difference:

builder/backend/artisan — the door for terminal commands 
$app = require_once __DIR__.'/bootstrap/app.php';

$status = $app->handleCommand(new ArgvInput);   // <-- handle a COMMAND
builder/backend/public/index.php — the door for web requests 
$app = require_once __DIR__.'/../bootstrap/app.php';

$app->handleRequest(Request::capture());        // <-- handle a REQUEST

Both files boot the same framework (both require the same bootstrap/app.php). They differ in one verb:

FileEntered byCallsIts job
artisan You, typing php artisan … in a terminal handleCommand() Run a command-line task (CLI)
public/index.php A browser, over HTTP handleRequest() Turn an HTTP request into an HTTP response

So the HTML you saw was built by public/index.php and the framework it boots — not by artisan.

Then what is php artisan serve doing?

serve is a command, so it comes through the artisan door. But its only job is to start a small web server (PHP's built-in development server) and point it at your public/ folder — then it sits there holding that server alive. Think of it as the building superintendent who unlocks the front door (public/index.php) and turns the lights on, then steps aside. Visitors walk through the door he unlocked; they don't walk through him. That's why the terminal is "busy", and why Ctrl+C kills the whole thing.

Here is the real chain for the welcome page — every step is a file you can open right now:

1
Browser sends GET /
To the dev web server that php artisan serve started on port 8000.
2
The web server runs public/index.php
The front door for every web request. It loads Composer's autoloader (which finds and loads the framework's classes on demand) and boots Laravel via bootstrap/app.php.
3
Laravel matches a route
bootstrap/app.php told it your routes live in routes/web.php. It looks there for one that matches /.
4
Your route's function runs
The matched route returns view('welcome'), which renders resources/views/welcome.blade.php into an HTML string.
5
That HTML goes back as a 200 OK
The browser paints it. artisan was never on this path — except that, earlier, you used it to start the server.
Reconciling M1-01's "it's not a file"

M1-01 said the page is not a file your browser opened — still true. There is a file involved (welcome.blade.php), but it's a recipe, not the finished dish: a template full of instructions ({{ … }}, @if) that gets executed to produce fresh HTML each request. No welcome.html is shipped byte-for-byte. The seam between "recipe" and "served as-is" is exactly what makes a backend a backend.

02What a route is

Step 3 above said "Laravel matches a route." A route is one rule that says: when a request with this method and this path arrives, run this function. The full set of rules is your app's routing table — a switchboard from (method, path) to your code.

Bridge — from what you know

You've built this exact thing before without the web vocabulary: a dict / switch mapping an incoming key to a handler function. ("GET", "/users/42") → showUser(42) is the same dispatch you'd write by hand in a socket server. Laravel just gives it a clean syntax and does the lookup for you.

You already have one route. Open builder/backend/routes/web.php — the whole file is essentially this:

builder/backend/routes/web.php — the route you already have 
Route::get('/', function () {
    return view('welcome');
});

Read it piece by piece — every part is a normal idea wearing PHP clothes:

PieceMeans
Route::get "Register a rule for the HTTP GET method." (There's Route::post, ::put, ::delete too — they map to the other HTTP verbs.)
'/' The path to match — here, the site root.
function () { … } The handler: the code that runs on a match. Whatever it returns becomes the response.

So the general shape of any route is just Route::<verb>('<path>', <handler>). That's the entire pattern you'll use for the rest of the project — the platform is, under the hood, a big pile of these.

A footgun to bank for later

If two routes share the same method and path, Laravel doesn't warn you — the last one you defined silently wins, and the earlier one is shadowed. Worth remembering the day a route "refuses to change."

03Just enough PHP to write a handler

PHP is new for you, so here is the minimum you need for today — no more. It's a C-family language; the shapes will feel familiar, with a few quirks:

php — illustrative, not your task 
$name   = 'Alex';                 // every variable starts with $
$scores = ['ctf' => 100];         // an array; 'ctf' => 100 is a key => value pair
                                  // (think Python dict / JS object)

function add($a, $b) {            // a named function
    return $a + $b;               // 'return' works just like you expect
}

$double = fn ($n) => $n * 2;      // an "arrow function": a one-line function value
PHPYou'd write, elsewhere…
$useruser (the $ is just mandatory punctuation)
['a' => 1, 'b' => 2]{"a": 1, "b": 2} (a dict / object)
function () { return 1; }a closure / lambda
fn () => 1the same closure, short form (like JS () => 1)
Why a function as an argument feels odd, and why it isn't

Passing function () { … } straight into Route::get is just a function used as a value — the same move as a JS callback or a Python function passed by name. Your rusty-JS instinct that "functions are values you can pass around" is exactly right here. Laravel stores your function and calls it later, only if a request matches.

04Whatever you return becomes the response

This is the load-bearing idea of the whole milestone. Your handler's return value is the HTTP response body. And every HTTP response also carries headers — small bits of metadata about the body — the most important here being Content-Type, which announces what kind of data the body is (HTML? JSON?) so the browser knows how to read it. Here's the payoff: Laravel sets that Content-Type for you, automatically, from the kind of thing you returned:

Your handler returns…Laravel sends…Content-Type
a string ('hello') that text as-is text/html
a view (view('welcome')) the rendered HTML page text/html
an array (['ok' => true]) that array, serialized to JSON — automatically application/json

That third row is the one to internalise. If a handler returns an array like this:

php — a value, to illustrate the rule 
$payload = ['status' => 'ok', 'points' => 100];
// returning $payload from a route → Laravel sends:  {"status":"ok","points":100}
Why this matters for OUR project

Our plan is Laravel as a JSON API + Vue as a separate frontend. That means our backend will mostly not generate HTML at all — it'll return data (JSON), and Vue (running in the browser) will build what the user sees. So "the page I see is HTML from a PHP process" is true for today's default welcome page, but for the platform itself, PHP emits JSON and the browser assembles the page. Laravel is already leaning this way: in bootstrap/app.php there's a line that says render errors as JSON for any /api/* route — a hint of the API to come.

05You don't restart the server for route changes

A practical thing that trips people up: after you edit routes/web.php, do you need to stop and restart php artisan serve? No. Just save the file and refresh the browser — your change is live.

Why: the dev server re-runs your app from public/index.php on every single request, re-reading your route files each time. This is PHP's classic "fresh start per request" model — different from a long-lived Node process that loads everything into memory once and holds it. (The one exception is if you ever run php artisan route:cache, which freezes the routes — you won't, so don't worry about it.)

06Check yourself

Predict each one before you reveal it — the predictions are the concept, and you'll confirm them for real in the checkpoint.

07Checkpoint — go build

Time to be the process that makes the response. Work in builder/backend/routes/web.php, below the existing / route. I'm describing the task, not handing you the code — writing it yourself is the whole point.

You're done when

You have two routes you wrote — one returning text, one returning JSON — both working in the browser, and you can explain, in your own words, why the array came back as JSON and which lines you added to which file.

Professional practice — naming the norm

This little change — your first real product code — is exactly the size of thing that deserves its own commit with a clear message. Professionals commit in small, logical units using Conventional Commits (e.g. feat: add ping and status routes). Don't commit builder/ just yet, though: remember M1-01 left a nested git repo inside builder/backend/. We'll settle that layout together first — then your first commit will be clean. For now, just know the norm exists; we'll practise it next.

If you get stuck

Tell me the exact route you wrote, what you expected, and what you actually saw (including any error text Laravel printed). A wrong response is a great thing to bring back — debugging it is half the learning.

When both routes work, come back and tell me — and bring any new questions that popped up. Then we cross to the other side of the wire: standing up the Vue app and having it call a route like the ones you just wrote. That's the round-trip that completes Milestone 1.
