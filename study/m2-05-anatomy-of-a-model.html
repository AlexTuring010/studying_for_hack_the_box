Anatomy of a Model

🎯  Goal: User.php stops being a black box 🔬  A line-by-line tour of your real file 🧩  Concept: what an Eloquent model is
Read me first

We've been editing app/Models/User.php — adding config, a cast, a trait — without ever properly touring it. Fair complaint. A model is the file type you'll edit most in Laravel, so let's dissect your User.php part by part until every line makes sense. A nice side effect: the Sanctum trait edit from the last lesson becomes obvious.

This one's about understanding, not building — read it, then poke your model in tinker to watch the pieces behave.

01What an Eloquent model actually is

A model is a PHP class that represents one database table. User stands for the users table; one instance of the class is one row. Instead of writing SQL, you talk to the table through the class:

the model IS your interface to the table 
User::create([...]);                 // INSERT a row
User::where('email', $e)->first();   // SELECT ... WHERE email = ?
$user->email;                        // read a column, as a property
$user->save();                       // UPDATE the row

You never told Laravel "User uses the users table" — it infers the table name from the class name (singular User → plural, lower-case users). The model is simply the PHP face of a table, and it's also where you configure how that table behaves. Which is exactly what the rest of the file does.

02Your User.php, line by line

Here's your actual file with markers — each number is explained below it.

builder/backend/app/Models/User.php (yours) 
<?php

namespace App\Models;                                       // (1)

use Database\Factories\UserFactory;                         // (2)
use Illuminate\Database\Eloquent\Attributes\Fillable;
use Illuminate\Database\Eloquent\Attributes\Hidden;
use Illuminate\Database\Eloquent\Factories\HasFactory;
use Illuminate\Foundation\Auth\User as Authenticatable;
use Illuminate\Notifications\Notifiable;

#[Fillable(['name', 'email', 'password'])]                  // (3)
#[Hidden(['password', 'remember_token'])]
class User extends Authenticatable                          // (4)
{
    /** @use HasFactory<UserFactory> */
    use HasFactory, Notifiable;                             // (5)

    protected function casts(): array                       // (6)
    {
        return [
            'email_verified_at' => 'datetime',
            'password' => 'hashed',
        ];
    }
}
#What it is
(1) namespace App\Models; — this class's "address." Its full name is App\Models\User, which is why you import it elsewhere as use App\Models\User;. Namespaces mirror folders: App\Models ↔ app/Models/.
(2) The import block — use …; lines that say where each referenced class lives. The interesting one: use Illuminate\Foundation\Auth\User as Authenticatable; imports Laravel's base auth-user class but renames it to Authenticatable in this file (that's what as does), so line (4) reads cleanly.
(3) Attributes (the #[…] syntax — like Java annotations / C# attributes: metadata on the class). Laravel reads them: #[Fillable] = the mass-assignment allowlist (what create() accepts); #[Hidden] = fields stripped from JSON output.
(4) class User extends Authenticatable — the class declaration. extends is inheritance (one parent only, in PHP). It extends the auth user base (not a plain Model), which is what gives users password-authentication abilities out of the box.
(5) The in-class trait line (mixins). HasFactory adds the factory() method (test data); Notifiable adds notify(). This is the line you add HasApiTokens to. The /** @use … */ line above it is just a PHPDoc comment for your editor/tooling — it doesn't run.
(6) casts() — tells Eloquent how to convert columns to/from PHP types. email_verified_at => 'datetime' makes that column a date object; password => 'hashed' auto-hashes on set. It's the type-conversion layer between the raw DB and your PHP objects.

03The two use keywords, again — because they're everywhere

Your file has use in both of its meanings, and telling them apart is half of reading Laravel fluently:

WhereMeaningIn your file
Top of file, before the class Import — "this class lives at this namespace path" the (2) block, e.g. use Illuminate\Notifications\Notifiable;
Inside the class body Trait — "mix these traits' methods into this class" line (5): use HasFactory, Notifiable;

A trait is PHP's mixin: since a class can extend only one parent, traits are how you graft in bundles of shared methods. That's why adding HasApiTokens to line (5) suddenly gives your User a createToken() method — the trait carries it in. And it needs a matching import up in (2) so PHP knows where HasApiTokens comes from. Two uses, one for "where," one for "mix in."

04Why your file looks different from most tutorials

If you Google "Laravel model fillable," almost every result shows this inside the class:

the OLDER style — property-based (not what you have) 
protected $fillable = ['name', 'email', 'password'];
protected $hidden   = ['password', 'remember_token'];

Your Laravel 13 uses the newer attribute form instead (#[Fillable([...])] / #[Hidden([...])] above the class). They mean exactly the same thing — same allowlist, same JSON hiding — just a newer syntax. So when a tutorial shows the $fillable property and your file shows the attribute, don't panic: they're two spellings of one idea. (You could even use the property form and it'd work; your scaffold just happens to ship the modern one.)

05Model vs migration: two halves of one table

Easy to conflate, worth separating cleanly:

MigrationModel
Jobdefines the table's structure (columns, types)reads/writes the table's rows + configures behaviour
Runs whenonce, at php artisan migrateevery time your code touches data
Lives indatabase/migrations/app/Models/

The migration built the users table (M2-01); the model is how you now use it. Same table, two files, two jobs.

07Checkpoint — see the model behave

No code to write — you'll read your model and then watch its parts act in tinker, so the annotations become real. (You need at least one registered user from M2-03; if first() is null, register one.)

You're done when

You can walk your User.php top to bottom and say what each part does, you've watched a cast and #[Hidden] behave in tinker, and the difference between the two use keywords is second nature.

If tinker fights you

User::first() returns null? You have no users yet — register one (M2-03) first. Class not found? Use the full \App\Models\User with the leading backslash inside tinker. Type exit to leave.
