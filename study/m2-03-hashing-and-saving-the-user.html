Hashing & Saving the User

🎯  Goal: your first real user row, password hashed 🔐  A core security practice (and the flag pattern in miniature) 🧩  Concept: hashing + Eloquent create
Read me first

Your endpoint validates — now it's time to actually save the user. Two ideas: hashing the password (so the raw password is never stored) and writing the row with Eloquent. Your User model is already set up to help — so much so that the real skill today is letting it do the work and not redundantly hashing the password yourself.

You'll edit your /register handler. I'll teach the concepts and your model's behaviour; you write the create call.

01Why passwords are hashed, never stored

Rule: never store a password you could read back. If your database ever leaks — and databases leak — plaintext passwords hand attackers every account at once, and (because people reuse passwords) their other accounts too. So you don't store the password. You store a hash of it.

A hash is a one-way function: easy to compute hash(password), effectively impossible to reverse hash → password. You keep the hash. Later, at login, you hash whatever the user typed and compare the two hashes — never the passwords themselves:

the one-way idea 
register:   store  hash("password123")   →   $2y$12$Xk9…   (a bcrypt hash)
login:      does  hash(typed_password)  ==  the stored hash?   → yes / no
            the real password is never written down anywhere
Salt & bcrypt (the one-liner)

Laravel hashes with bcrypt by default, which mixes in a random salt — so two people with the same password get different hashes, defeating precomputed "rainbow table" attacks. You get all of this for free; you just have to use it and not fight it.

This is the flag pattern, early

Bank this: it's exactly how we'll handle CTF flags in M4. We won't store the real flag — we'll store its hash, and when a player submits a guess we'll hash their guess and compare. Same principle: the server never keeps the secret itself, only a fingerprint of it. Learn it here on passwords; reuse it there on flags.

02Your User model already hashes for you

Open app/Models/User.php. Three lines shape everything you do today:

builder/backend/app/Models/User.php — the parts that matter 
#[Fillable(['name', 'email', 'password'])]      // which fields create() will accept
#[Hidden(['password', 'remember_token'])]        // stripped from JSON responses
// ...
protected function casts(): array {
    return [
        'password' => 'hashed',                   // ← auto-hash the password on set
    ];
}
LineWhat it does for you
'password' => 'hashed' When you set password on the model, Laravel hashes it automatically. You hand it the plain password; it stores the hash.
#[Hidden([...])] The password is removed from any JSON the model produces — so returning the user won't leak the password (last lesson's problem, gone).
#[Fillable([...])] The mass-assignment allowlist: create() only accepts these fields — name, email, password.
Keep hashing in exactly ONE place

Because the cast already hashes, you should not also call Hash::make() on the password before saving. It won't crash or lock anyone out — the cast is idempotent: it first checks whether the value is already hashed (Hash::isHashed) and, if so, leaves it untouched, so you'd still end up with one valid hash and login would still work. But hashing it yourself is redundant, and it leans on that already-hashed detection instead of a clear rule. Keep hashing in exactly one place — the cast. Hand create() the plain validated password and let the model do its job. (You'll meet Hash::check() next lesson, for login — but you never need Hash::make() here.)

Why #[Fillable] exists — a security allowlist

Mass assignment means handing an array straight into create(). Without an allowlist, a crafted request could set fields you never intended — imagine someone slipping "is_admin": true into the JSON. #[Fillable] says "only these columns may be set this way," so extras are ignored. Another quiet security default you're already benefiting from. (Older Laravel writes this as protected $fillable = [...] — same idea, property instead of attribute.)

03Writing a row: Model::create()

Eloquent's create() inserts a row from an array and hands you back the new model — no SQL. Here's the shape on a made-up model:

php — Eloquent create (illustrative, NOT your task) 
use App\Models\Post;

$post = Post::create([
    'title' => 'Hello',
    'body'  => 'World',
]);
// $post is the saved row — it now has an id, created_at, etc.
return $post;   // serialised to JSON automatically

Two things to notice: you use the model class (like any import), and the returned model is your response — Laravel serialises it to JSON, honouring #[Hidden]. Applied to registration: create a User from your validated data (which is already exactly name, email, password), and return the new user. The cast hashes the password on the way in; #[Hidden] hides it on the way out. You write no hashing code at all.

04The payoff: unique:users finally bites

Last lesson you registered the same email twice with no error, and we said: that's because nothing was being saved, so unique:users had an empty table to check. The moment your handler actually writes a row, that changes:

1
First registration of an email
Table has no such row → validation passes → a user is created. Table now has 1 row.
2
Second registration of the SAME email
unique:users now finds the existing row → validation fails → 422, "email already taken". The puzzle from last lesson, solved.

So saving the user makes your validation come fully alive. You'll verify exactly this in the checkpoint.

You're done when

Registering creates a real row whose password is a bcrypt hash (not plaintext), the API response omits the password, and a duplicate email is rejected with a 422 — and you can explain why we hash and why you must not hash it yourself given the cast.

If something's off

Password saved as plaintext? The casts() entry is missing or the field name isn't password. Class 'App\\Models\\User' not found? Add the use App\\Models\\User; import. Mass-assignment error / fields ignored? Check #[Fillable] lists the fields you're passing. Paste me the error and what tinker shows.
