M2 · Users Exist Concept 4

Auth Tokens & Installing Sanctum

🎯  Goal: the plumbing that keeps a user logged in 🆕  A new package — installed the safe way 🧩  Concept: stateless HTTP & bearer tokens
Read me first

You can create users. Now they need to log in — and, crucially, stay logged in across page loads and API calls. That needs a way to prove "I'm still me" on every request. The answer is an auth token, and the tool that issues them in Laravel is Sanctum.

This lesson is the concept plus setup — installed carefully, because the usual one-command installer would clash with the API routing you wired by hand. Next lesson you'll build the login endpoint that actually hands out a token.

01The problem: HTTP forgets you instantly

HTTP is stateless: every request is an island. Your server handles a request, sends a response, and remembers nothing about you for the next one. So the instant after a successful login, the very next request arrives as a total stranger. How does request #2 know it's the same person who logged in on request #1?

There are two classic answers:

Sessions (cookies)Tokens
Who remembersthe server (keeps a session; browser holds a cookie)the client (holds a token string)
Sent howa cookie, automatically by the browseran Authorization header you set
Best fita classic server-rendered sitea separate SPA + API — like yours

Because your Vue app and Laravel API are two separate origins talking over HTTP, tokens are the natural fit — and the path we'll take.

02What an auth token is

A token is a long, random secret string the server hands you when you log in. The client stores it, and sends it on every later request in a header:

how the client proves who it is, every request 
Authorization: Bearer 3|k9Xf2p…the-long-random-token…

The server reads that header, looks the token up, and knows who you are — no session needed. The word "bearer" is the key idea: whoever bears (holds) the token is treated as you. It's a wristband at a festival — you prove your ID once at the gate, get a wristband, and after that you just flash the wristband instead of re-proving yourself.

Security consequences (your HTB lens)

Two things follow from "whoever holds it is you." One: a token is a live credential — leak it (in a URL, a log, an insecure store) and someone else becomes you, so it travels over HTTPS and is stored carefully. Two: the server never stores the token in plaintext either — Sanctum keeps only a hash of it in the database (SHA-256). Sound familiar? Same rule as passwords, same rule as flags: never store the raw secret, only a fingerprint.

03Sanctum: Laravel's token issuer

Laravel Sanctum is the official package for API tokens. It gives you three things: a personal_access_tokens table to store tokens (hashed), a createToken() method on your User model, and a guard (auth:sanctum) that checks the Authorization header on protected routes. Today you install it and wire the model; issuing and checking tokens come in the next two lessons.

Sanctum has two modes — we want the simple one

Sanctum can do cookie-based "SPA authentication" (with stateful domains, a CSRF cookie, etc.) or plain API tokens. We're using tokens — simpler, and a perfect fit for a separate frontend. So you'll ignore anything about SANCTUM_STATEFUL_DOMAINS, config/sanctum.php, or a CSRF cookie: token auth needs zero config. Install, migrate, add a trait — done.

04Installing Sanctum — the safe path

⛔ Do NOT run php artisan install:api here

You'll see that command in most tutorials — but you already created routes/api.php and registered api: in bootstrap/app.php by hand. Plain install:api would just print a confusing red "API routes file already exists" error, and running it with --force would overwrite your api.php (destroying /register) and duplicate your routing into a fatal error that stops the whole app booting. Use the three manual steps below instead — they can't touch your routes.

Three steps, run in builder/backend/:

1 — install the package (needs internet) 
composer require laravel/sanctum
# no version pin — composer picks the newest Sanctum compatible with your Laravel 13.
# (Pinning an old version like :^4.0 fails: Sanctum 4.0.0 needs Laravel 11, not 13.)
2 — create its table (Sanctum ships the migration; Laravel loads it) 
php artisan migrate
# then confirm it landed:
php artisan migrate:status        # look for ...create_personal_access_tokens_table  → Ran

Step 3 — give your User the token power. In app/Models/User.php, import Laravel\Sanctum\HasApiTokens at the top, and add HasApiTokens to the model's existing trait line (the one that currently reads use HasFactory, Notifiable;). That trait is what adds the createToken() method — without it, issuing a token later would fatal. (You make this edit; it's the same "add to the trait list" shape you can see already in the file.)

05Prove the plumbing works (before any endpoint)

Before you build a login endpoint on top, confirm the foundation works in isolation. php artisan tinker lets you poke your app live. Grab your registered user and mint a token:

in php artisan tinker 
$u = \App\Models\User::first();
$u->createToken('test')->plainTextToken;     // → "1|abc123…"  (your first token!)

That string is the token a client would carry. Two things to notice, both reinforcing the security theme:

  • The format is <id>|<random>. The plainTextToken is shown once — right now — and never again.
  • Look at what got stored: php artisan db:table personal_access_tokens shows a row, but the token column holds a hash, not the string you just saw. Same one-way principle as passwords. If the DB leaks, the tokens in it can't be used directly.

06Check yourself

Predict each before revealing it.

07Checkpoint — install & verify Sanctum

Set up the token foundation and prove it works — no endpoint yet. Run in builder/backend/.

You're done when

Sanctum is installed, the personal_access_tokens table exists, your User model can createToken() (proven in tinker), and you can explain why a stateless API needs a token and why the token is stored hashed.

If a step misbehaves

composer fails? Check your internet and that composer is on your PATH. migrate:status doesn't list the token migration? Publish it first, then migrate again: php artisan vendor:publish --provider 'Laravel\Sanctum\SanctumServiceProvider' (single backslashes, single-quoted), then php artisan migrate. createToken() not found in tinker? The HasApiTokens trait/import is missing from User.php. Paste me the exact error.

Once you can mint a token, come back and tell me. Then the endpoint that makes it real: login — take an email and password, verify them with Hash::check(), and on success return one of these tokens. We'll also handle "wrong credentials" the secure way — without leaking whether it was the email or the password that was wrong (a small anti-enumeration detail attackers love when it's missing).
