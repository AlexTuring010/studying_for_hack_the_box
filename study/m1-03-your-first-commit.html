M1 · Plumbing Concept 3

Your First Commit

🎯  Goal: your routes become a saved point in history 🔐  Practice: keep secrets out of git, forever 🧩  Concept: the staging model + a scoped commit
Read me first

Last lesson you wrote real product code — two routes that are genuinely yours. Right now that code exists only as edited bytes in one folder on one machine. This lesson turns it into a commit: a permanent, labelled save-point in your project's history — the unit professionals work in, and the thing that later proves you built this.

Good news up front: the nested-repo worry from M1-01 is already gone (we'll confirm it below), so your first commit is clean by construction. Everything here points at real files and real commands you'll run in builder/ — but note the professional why behind each, because that's the interview-grade part.

01One repo covers everything (and the nested-repo scare is over)

A git repository is just a folder with a hidden .git/ subfolder inside it. That .git/ is the whole database — every commit, every version, the entire history — for everything beneath it. Your project has exactly one, at the very top:

the one repo boundary — one .git, at the root 
studying_for_hack_the_box/
├── .git/            <-- THE repository. tracks everything below.
├── CLAUDE.md        (Claude commits this)
├── study/           (Claude commits this — the site you're reading)
└── builder/         (YOU commit this — your product code)
    └── backend/     your Laravel app lives here
        └── routes/web.php

So study/ and builder/ are not separate projects — they're two folders inside one repo. That's deliberate: the history honestly shows both the teaching material and your build side by side.

Why "nested repo" was a real worry — and why you're clear

When you ran laravel new in M1-01, the installer quietly did git init inside builder/backend/, creating a second .git/ — a repo inside a repo. Git hates that: the outer repo can't see inside a folder that has its own .git/, so your Laravel app would have shown up as one opaque blob (or an accidental "submodule"), and your files wouldn't really be tracked. That nested .git/ has since been removed, so you're on the clean path. One command proves it — run it from inside the backend:

"which repo am I actually in?" 
git rev-parse --show-toplevel

If it prints the path ending in studying_for_hack_the_box (the root) — good, one repo. If it ever printed …/builder/backend, that would mean a nested repo had come back.

02The three areas: working tree → staging → commit

Your JS is rusty and your git may be too, so here's the one mental model the rest of this depends on. A commit isn't made in one step — your changes pass through three areas, and you control the gate between each:

1
Working tree — your files as they are right now
The actual files on disk, including your edits to web.php. Git sees them as "changed" but hasn't been told they matter yet. git status shows you this.
2
Staging area (the "index") — what you've chosen for the next commit
git add <path> copies a change into a holding pen. Nothing is saved yet — you're assembling the next snapshot, deciding exactly what goes in.
3
History — a sealed, labelled commit
git commit -m "…" freezes whatever is staged into a permanent snapshot with a message. This is the save-point. git log shows the chain of them.
Bridge — from what you know

Think of it like sending a parcel: the working tree is your whole desk, the staging area is the box you're packing (you choose what goes in), and the commit is sealing and posting it with a label on top. The reason git splits "pack" from "post" is so you can commit a clean, logical subset — not just dump the entire desk every time.

CommandWhat it does
git statusShow what changed and what's currently staged. Run it constantly.
git add <path>Stage a file or folder for the next commit.
git add -n <path>Dry run — list what would be staged without staging it. Your safety check.
git commit -m "msg"Seal everything staged into a labelled save-point.
git log --onelineShow the history, one commit per line.

03What you must never commit: secrets & generated code

This is the professional heart of the lesson. A commit is forever and the repo is shared (it's on GitHub). Two kinds of files must stay out:

Never commitWhy
Secrets — .env Holds your APP_KEY and database credentials. A secret committed to git history is leaked — deleting it later doesn't help, git remembers every version. This is the classic career-defining mistake; don't make it.
Generated / vendored code — vendor/, node_modules/ Thousands of files you didn't write, rebuilt on demand from composer.lock / package-lock.json. Committing them bloats the repo and hides your actual work in the noise.
Local machine state — *.sqlite, logs, caches Your local database file and logs are yours alone — not part of the shared source. Each dev creates their own.

You don't police this by hand — that's what a .gitignore file is for. Each line is a pattern; git silently refuses to stage anything that matches. You already wrote a good one at the repo root:

.gitignore (root) — the parts that matter here 
# Dependencies
vendor/

# Environment files (never commit real secrets)
.env
.env.*
!.env.example        # the ! UN-ignores this one

# Local database
*.sqlite
The !.env.example trick — and why it's clever

.env.* ignores every env file. Then !.env.example punches one exception back in. Why keep that one? Because .env.example is a blank template — the same keys (DB_DATABASE=, APP_KEY=) with the values stripped out. A teammate clones the repo, copies .env.example to .env, and fills in their own secrets. You commit the shape of the config, never the secret values. Real, live secrets go through the door and are never seen.

The pro habit: look before you commit

Never blind-commit. Before sealing anything, ask git to show you what it would stage. A dry run of adding your whole backend prints a clean list — no vendor/, no .env:

list-only — nothing is staged by this 
git add -n builder/

# add 'builder/backend/.env.example'   <-- template: yes
# add 'builder/backend/composer.json'
# add 'builder/backend/routes/web.php' <-- your routes: yes
# ... ~57 real source files ...
# (no builder/backend/.env  ·  no builder/backend/vendor/**)

Seeing .env.example present but .env absent is the proof your .gitignore is doing its job. Then you commit.

04Make it scoped, make it labelled

Two professional norms turn "a commit" into "a good commit."

Scope — your commit contains only your work

The history should honestly say who did what. study/ and CLAUDE.md are Claude's and are already committed — they are not yours to commit. So you stage only builder/:

stage your work, and nothing but your work 
git add builder/          # ✅ scoped to your product code
# NOT: git add -A         # ❌ sweeps in anything lying around

This is why git add -A / git add . are a habit worth not forming: they don't think about boundaries, and one day they'll catch a file you never meant to include.

Label — a Conventional Commit message

The message is a headline for your future self and your teammates. The team standard for this project is Conventional Commits:

the shape of a commit message 
<type>: <short, imperative summary>

# type is one of:  feat  fix  docs  chore  refactor  test  …
# feat  = a new capability      chore = scaffolding / plumbing
# good:  feat: add example text and JSON routes
# weak:  update            (says nothing)
# weak:  Added some routes because I was learning…   (that's a body, not a subject)
Honest history: this first commit is mostly scaffold

Reality check — your first commit brings in the whole Laravel skeleton (57 files), of which you personally wrote about three lines. So an honest single message names both: something like chore: add Laravel backend scaffold and first routes. The pro move (optional, if you want the practice) is two commits — one chore: for the untouched scaffold, then one feat: for your routes — so the history cleanly separates "vanilla Laravel" from "what Alex added." Either is fine today; write the message yourself either way.

05The next habit (not today): branches & pull requests

You'll commit straight to main this once — it's your first commit, you're solo, and keeping the mechanics minimal lets the ideas above land. But bank where this is heading: professionals rarely commit product code straight to main. They branch (git switch -c feat/…), commit there, push, and open a Pull Request — a reviewable proposal to merge — so a teammate reads it before it joins the main line.

We'll adopt that flow deliberately once your GitHub remote starts pulling its weight (there's already an origin waiting). For now: one clean, honest commit. The branch-and-PR muscle comes next.

06Check yourself

Predict each before you reveal it — then you'll confirm the real thing in the checkpoint.

07Checkpoint — commit your work

Turn your routes into history. Work from the project root (studying_for_hack_the_box/) in your terminal. I'm describing the steps, not handing you a script — run them yourself and read what each one says back.

You're done when

git log --oneline shows your own commit containing your backend, and you can explain, in your own words, (a) why .env must never be in there and (b) why staging only builder/ (not -A) is the honest, professional move.

If something looks off

If the dry run lists .env, a vendor/ path, or a .sqlite file — stop, don't commit, and tell me exactly what you saw. That's a .gitignore not matching, and it's much easier to fix before the commit than after. Bringing me a surprised "wait, why is this in the list?" is a great outcome.

When your commit is in, come back and paste your git log --oneline — and bring any questions the commands raised. Then we cross to the browser: standing up the Vue app and having it fetch one of the routes you just committed. That round-trip is the last piece of Milestone 1.
