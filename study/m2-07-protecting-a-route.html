M2 · Users Exist Concept 7

Protecting a Route

🎯  Goal: a route that only a valid token can reach 🚪  Middleware as a gate, auth:sanctum as the guard 🧩  Concept: middleware + $request->user()
Read me first

Login hands back a token — but right now that token is a key to a door that doesn't exist. Every route in your app is wide open; nothing checks for the token. This lesson builds the door: a protected route that rejects anyone without a valid token (401), and lets a valid one through and tells you who they are.

That completes the arc of M2: register → login → make an authenticated request. The mechanism is middleware — a new Laravel idea, taught properly below — and one line of it (auth:sanctum) does the work.

01Right now your token does nothing

Think about what you've actually got after login: a token string sitting in the response. But none of your existing routes — /register, /login, /test-php-array, and the rest — ever look at any token; they run for anybody who calls them. So the token is real, but nothing in your app requires it or reacts to it yet.

To make it matter you need two things, and this lesson delivers both:

  • A gate — a route that says "no valid token, no entry" and answers 401 Unauthorized to anyone without one.
  • An identity — once someone's through the gate, a way to know which user this is, so the route can act on their behalf.

You already met the client side of this in M2-04: the caller proves themselves by sending Authorization: Bearer <token> on the request. Now you build the server side that checks it.

02Middleware: code that runs before your handler

Middleware is a filter that sits in front of your route handler in the request pipeline. Every request passes through the middleware first; the middleware can let it through, tweak it, or reject it outright — and if it rejects, your route code never runs at all.

Mental model — a bouncer at the door

A request wants to reach your handler. Middleware is the bouncer between the street and the room: it checks your credentials at the door. Pass, and you walk in and the handler serves you. Fail, and you never get inside — the bouncer turns you away right there. You can stack several bouncers (logging, rate-limiting, auth); the request has to clear each one in turn. (If you've seen Express middleware, it's the same idea; if you've seen a decorator wrapping a function, also the same shape — a wrapper that runs first.)

You don't write the auth middleware yourself — Laravel and Sanctum ship it. Your job is just to attach it to the routes you want guarded. The specific bouncer you want is called auth:sanctum.

03The auth:sanctum guard, step by step

When you attach auth:sanctum to a route, here's what runs on every request before your handler — for free, no code from you:

1
Read the header
It looks for Authorization: Bearer <token> on the request. No such header → straight to a 401.
2
Verify the token
It finds that token's row in personal_access_tokens and checks it by hashing the presented token and comparing to the stored hash — the same never-store-raw principle you used for passwords (M2-03/M2-04). One nuance: tokens use a fast SHA-256 hash, not the slow bcrypt used for passwords — safe here because a token is long, high-entropy random data with nothing to guess, unlike a human password.
3
Resolve the user — or reject
Valid → it loads the User that token belongs to and attaches them to the request, then lets it through. Missing / wrong / revoked → it short-circuits with 401 Unauthorized and your handler never runs.
4
Your handler runs — authenticated
Only genuine, token-bearing requests reach your code. And because step 3 already identified the user, you can just ask for them (§5).
The 401 comes back as JSON — your setup already handles it

Because you configured Laravel to render JSON for api/* (M2-02), a rejected request gets a clean 401 with { "message": "Unauthenticated." } — not an HTML redirect to a login page. Zero extra Sanctum config, same as when you set up tokens: token auth Just Works from the pieces you already installed.

04Attaching auth:sanctum to a route

You attach middleware with ->middleware(...). Here's the shape on a made-up route (not your task — the pattern):

php — attach middleware to ONE route (illustrative) 
Route::middleware('auth:sanctum')->get('/example', function (Request $request) {
    // only reached if the Bearer token was valid
    return 'you are in';
});

Once you have several routes that all need a login, don't repeat ->middleware(...) on each — wrap them in a group so the gate applies to all of them at once:

php — one gate for many routes (illustrative) 
Route::middleware('auth:sanctum')->group(function () {
    Route::get('/example',  /* ... */);
    Route::post('/another', /* ... */);
    // every route in here is protected
});

For today one protected route is enough, so the single-route form is fine — but the group is worth knowing, because M3+ will pile up routes that all require a logged-in user.

05Knowing who's calling: $request->user()

Inside a route guarded by auth:sanctum, the middleware has already figured out who the token belongs to. So you don't look anyone up — you just ask:

php — the authenticated user (textbook line) 
$request->user();   // → the User model this request's token belongs to
                    // (in a PROTECTED route it's never null — the gate guaranteed it)

Notice the contrast with your /login route. There, nobody was authenticated yet, so you had to find the user by email and verify the password by hand. In a protected route that work is already done — $request->user() hands you the logged-in user directly. That's the payoff of the token: after login, the server can identify the caller on every request without them re-sending a password.

401 vs 403 — a quick distinction

401 Unauthorized = "I don't know who you are" (no/invalid token) — what auth:sanctum returns. 403 Forbidden = "I know who you are, but you're not allowed to do this" (e.g. a normal user hitting an admin-only action). Today is all 401; 403 shows up later when some users can do things others can't.

06Which routes are public, which are protected?

This is a real design decision, and it has a trap in it. It's tempting to "secure everything." But look what happens if you put auth:sanctum on /login:

RoutePublic or protected?Why
POST /register Public A brand-new user has no token yet — requiring one would make signup impossible.
POST /login Public Login is how you get a token. Requiring a token to log in is a chicken-and-egg deadlock — nobody could ever authenticate.
your new "who am I" route Protected It answers "who is the logged-in user?" — meaningless without a login, so it belongs behind the gate.

The rule: routes that hand out tokens (register, login) stay open; routes that need a logged-in user go behind auth:sanctum. When M4 adds "submit a flag," that endpoint will be protected too — only real, logged-in players score.

08Checkpoint — build a protected route & close the loop

Add one protected route that reports the logged-in user, then prove the gate works from both sides. Every piece is shown above; you choose the route, attach the middleware, and test it.

You're done when

The same route returns 401 with no token and 200 + your user with a valid Bearer token — and you can explain what the auth:sanctum middleware did in between, and why /login had to stay public.

If something's off

401 even with a token? Check the header is exactly Authorization: Bearer <token> (the word Bearer, a space, then the full id|string token from login — not a truncated copy). Getting HTML or a redirect instead of JSON 401? The request isn't being treated as api/* JSON — confirm you're calling the /api/... URL. 500, not 401/200? Likely a syntax slip in the new route — read the php artisan serve terminal or php artisan route:list for the real error (the browser's CORS message is a red herring, remember). When the gate turns away a tokenless request and welcomes a valid one, you've closed the whole authentication loop: register → login → authenticated request. That's the backend of M2 essentially complete. From here we turn to the Vue side — building the register/login forms, storing the token in the browser, and sending it as a Bearer header on protected calls so the UI has an "logged-in" state — and then on to M3, where challenges appear.

Follow-up You asked · going deeper

↳Is the users table special? (could a companies table have tokens too?)

The question

In §03 I said the guard "finds that token's row and loads the User it belongs to." Fair question: how does it know the token pairs with a user — that it was made by $user->createToken(...) for a row in the users table? Is users somehow the special table Sanctum is wired to? No — and that's the elegant part. The short answers: the owner is written down when the token is created (not guessed later), and yes, a companies table could own tokens in the exact same way. Below is the real mechanism, with the PHP-isms unpacked as we hit them — none of this is your build task, it's Sanctum's own plumbing.

First, the PHP words you'll see

You don't come from PHP, and this bit leans on a few PHP/Laravel-specific things. Here's the pocket dictionary so the rest reads smoothly — skim it, then refer back:

You'll seeWhat it actually is (in plain terms)
use X; inside a class Applies a trait. A trait is a pre-written bundle of methods a class can absorb — writing use HasApiTokens; inside a class pours all of that trait's methods (like createToken()) straight into it. It's PHP's version of a mixin: the closest thing to "inheriting" behaviour from something that isn't a parent class. This one line is what makes a model "able to have tokens."
use X; at the top of a file Same keyword, completely different job: an import. It just lets you type the short name Request instead of the full Illuminate\Http\Request. So: top-of-file use = import a name; in-class-body use = apply a trait. Don't let the shared keyword fool you.
App\Models\User and the \ A class's fully-qualified name — its full "address" in the codebase. The backslash \ is just the separator between namespaces (folders-of-code) — not a file path and not an escape character. Hold onto this: Laravel stores this whole string in a column to remember which kind of model owns a token.
User::class Evaluates to that fully-qualified name as a plain string ("App\Models\User"). Useful when code needs to name a class rather than use one.
$obj->thing vs Class::thing() -> reaches into a specific instance ($user->id = "this user's id"). :: calls something on the class itself, no instance needed (PersonalAccessToken::findToken(...)). Two different arrows for two different targets.
explode('|', $s, 2) PHP's string split — exactly JavaScript's $s.split('|'). The 2 caps it at two pieces. It returns an array, and [$id, $rest] = explode(...) destructures it, just like array destructuring in JS.

The owner is written down, not figured out

Here's the one idea that dissolves the whole confusion: the middleware never deduces who owns a token — it just reads a note that was saved when the token was born. When you ran $user->createToken('auth-token'), Sanctum did roughly this (its own code, trimmed):

php — Sanctum's createToken, the essential lines 
$token = $this->tokens()->create([        // $this is the User that called createToken
    'name'  => $name,
    'token' => hash('sha256', $plainTextToken),   // stores a HASH, never the raw token
    // ...
]);
return $token->getKey() . '|' . $plainTextToken;  // hands you  "7|aB9x..."

The interesting column is one you might expect to be called user_id — but open your own migration (...create_personal_access_tokens_table.php) and there's no such column. Instead the line $table->morphs('tokenable') created two columns. When $user->createToken() inserts the row, they get filled in like this:

columnvaluewhat it means
id7this token's own row number
tokenable_typeApp\Models\Userwhich kind of thing owns it
tokenable_id5which one — User #5
token9f2a… (sha256)the hashed secret
The key concept — a polymorphic relationship

A normal foreign key is one column (user_id = 5) that can only ever point at the users table. Sanctum instead uses a polymorphic relationship: a two-column foreign key — tokenable_type says which table/model, tokenable_id says which row in it. That pair can point at any model, not just users. In Laravel's ORM (Eloquent) the two sides are named morphMany ("a User has many tokens") and morphTo ("a token belongs to… whatever tokenable_type says"). The word "morph" is the tell that the target type isn't fixed.

What actually makes a model "tokenable": the trait, not the name

So is users the special table Sanctum knows about? Look at the exact test the guard uses to decide whether something is allowed to own a token (its own code):

php — Sanctum's guard, the "can this thing own tokens?" check 
in_array(HasApiTokens::class, class_uses_recursive(get_class($tokenable)))
//        └ the trait's name        └ "list every trait this class uses"

Read it in English: "does the model that owns this token use the HasApiTokens trait?" That's the whole gate. It asks about a trait, never about the class being User. There is no hard-coded reference to users anywhere in the token flow. The users table isn't special — it just happens to be the one model in your app that currently carries use HasApiTokens; (you can see that line in your app/Models/User.php).

And on the way back in: how 7|aB9x... becomes User #5

This also explains the "id|token" shape from the login response that §03 glossed over. The part before the | is literally that row's id. So verifying an incoming Authorization: Bearer 7|aB9x... is fast and direct:

1
Split on the |
[$id, $secret] = explode('|', $token, 2) → "7" and "aB9x...". The id tells it exactly which row to open — a primary-key lookup, no scanning the whole table.
2
Hash-check the secret
It hashes the presented "aB9x..." and constant-time-compares it to the token hash stored in row #7. Match → real token; mismatch → rejected. (Same never-store-raw idea as §03.)
3
Follow tokenable_type + tokenable_id home
Row #7 says App\Models\User / 5, so Eloquent builds a User from row 5 of users. That instance is what $request->user() hands you.

So yes — a companies table could have tokens too

Your instinct was exactly right. Because nothing hard-codes User, the recipe for "let companies authenticate with tokens" is a single trait on a Company model:

php — illustrative: any model can become tokenable 
class Company extends Model
{
    use HasApiTokens;   // ← the entire requirement
}

// then, exactly like a user:
$company->createToken('api');   // row: tokenable_type = App\Models\Company, tokenable_id = <company id>

Those company tokens land in the same personal_access_tokens table as the user tokens, told apart purely by tokenable_type. A request bearing one resolves, step-3 above, back to a Company instance instead of a User. One polymorphic table, many kinds of owner.

One wrinkle, for later — not now

Creating and verifying company tokens works out of the box as described. The one extra knob is the Sanctum guard's provider: if you ever want both users and companies logging in, you'd give them separate guards so each protected route knows which kind of caller it expects. Default single-model setups (what you have) don't touch this at all — file it under "M-way-later," not today.

Why this rhymes with your own project

This is the same instinct behind the challenges.type field in our plan (static / shared_container / per_user_instance): record what kind of thing in a column so one table/mechanism can serve many cases, instead of hard-coding a single type and rewriting later. Sanctum does it with tokenable_type; we'll do it with a challenge type. Spotting that pattern in a real library is exactly the muscle we're building.
