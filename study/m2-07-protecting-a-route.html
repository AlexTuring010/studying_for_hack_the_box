M2 · Users Exist Concept 7

Protecting a Route

🎯  Goal: a route that only a valid token can reach 🚪  Middleware as a gate, auth:sanctum as the guard 🧩  Concept: middleware + $request->user()
Read me first

Login hands back a token — but right now that token is a key to a door that doesn't exist. Every route in your app is wide open; nothing checks for the token. This lesson builds the door: a protected route that rejects anyone without a valid token (401), and lets a valid one through and tells you who they are.

That completes the arc of M2: register → login → make an authenticated request. The mechanism is middleware — a new Laravel idea, taught properly below — and one line of it (auth:sanctum) does the work.

01Right now your token does nothing

Think about what you've actually got after login: a token string sitting in the response. But none of your existing routes — /register, /login, /test-php-array, and the rest — ever look at any token; they run for anybody who calls them. So the token is real, but nothing in your app requires it or reacts to it yet.

To make it matter you need two things, and this lesson delivers both:

  • A gate — a route that says "no valid token, no entry" and answers 401 Unauthorized to anyone without one.
  • An identity — once someone's through the gate, a way to know which user this is, so the route can act on their behalf.

You already met the client side of this in M2-04: the caller proves themselves by sending Authorization: Bearer <token> on the request. Now you build the server side that checks it.

02Middleware: code that runs before your handler

Middleware is a filter that sits in front of your route handler in the request pipeline. Every request passes through the middleware first; the middleware can let it through, tweak it, or reject it outright — and if it rejects, your route code never runs at all.

Mental model — a bouncer at the door

A request wants to reach your handler. Middleware is the bouncer between the street and the room: it checks your credentials at the door. Pass, and you walk in and the handler serves you. Fail, and you never get inside — the bouncer turns you away right there. You can stack several bouncers (logging, rate-limiting, auth); the request has to clear each one in turn. (If you've seen Express middleware, it's the same idea; if you've seen a decorator wrapping a function, also the same shape — a wrapper that runs first.)

You don't write the auth middleware yourself — Laravel and Sanctum ship it. Your job is just to attach it to the routes you want guarded. The specific bouncer you want is called auth:sanctum.

03The auth:sanctum guard, step by step

When you attach auth:sanctum to a route, here's what runs on every request before your handler — for free, no code from you:

1
Read the header
It looks for Authorization: Bearer <token> on the request. No such header → straight to a 401.
2
Verify the token
It finds that token's row in personal_access_tokens and checks it by hashing the presented token and comparing to the stored hash — the same never-store-raw principle you used for passwords (M2-03/M2-04). One nuance: tokens use a fast SHA-256 hash, not the slow bcrypt used for passwords — safe here because a token is long, high-entropy random data with nothing to guess, unlike a human password.
3
Resolve the user — or reject
Valid → it loads the User that token belongs to and attaches them to the request, then lets it through. Missing / wrong / revoked → it short-circuits with 401 Unauthorized and your handler never runs.
4
Your handler runs — authenticated
Only genuine, token-bearing requests reach your code. And because step 3 already identified the user, you can just ask for them (§5).
The 401 comes back as JSON — your setup already handles it

Because you configured Laravel to render JSON for api/* (M2-02), a rejected request gets a clean 401 with { "message": "Unauthenticated." } — not an HTML redirect to a login page. Zero extra Sanctum config, same as when you set up tokens: token auth Just Works from the pieces you already installed.

04Attaching auth:sanctum to a route

You attach middleware with ->middleware(...). Here's the shape on a made-up route (not your task — the pattern):

php — attach middleware to ONE route (illustrative) 
Route::middleware('auth:sanctum')->get('/example', function (Request $request) {
    // only reached if the Bearer token was valid
    return 'you are in';
});

Once you have several routes that all need a login, don't repeat ->middleware(...) on each — wrap them in a group so the gate applies to all of them at once:

php — one gate for many routes (illustrative) 
Route::middleware('auth:sanctum')->group(function () {
    Route::get('/example',  /* ... */);
    Route::post('/another', /* ... */);
    // every route in here is protected
});

For today one protected route is enough, so the single-route form is fine — but the group is worth knowing, because M3+ will pile up routes that all require a logged-in user.

05Knowing who's calling: $request->user()

Inside a route guarded by auth:sanctum, the middleware has already figured out who the token belongs to. So you don't look anyone up — you just ask:

php — the authenticated user (textbook line) 
$request->user();   // → the User model this request's token belongs to
                    // (in a PROTECTED route it's never null — the gate guaranteed it)

Notice the contrast with your /login route. There, nobody was authenticated yet, so you had to find the user by email and verify the password by hand. In a protected route that work is already done — $request->user() hands you the logged-in user directly. That's the payoff of the token: after login, the server can identify the caller on every request without them re-sending a password.

401 vs 403 — a quick distinction

401 Unauthorized = "I don't know who you are" (no/invalid token) — what auth:sanctum returns. 403 Forbidden = "I know who you are, but you're not allowed to do this" (e.g. a normal user hitting an admin-only action). Today is all 401; 403 shows up later when some users can do things others can't.

06Which routes are public, which are protected?

This is a real design decision, and it has a trap in it. It's tempting to "secure everything." But look what happens if you put auth:sanctum on /login:

RoutePublic or protected?Why
POST /register Public A brand-new user has no token yet — requiring one would make signup impossible.
POST /login Public Login is how you get a token. Requiring a token to log in is a chicken-and-egg deadlock — nobody could ever authenticate.
your new "who am I" route Protected It answers "who is the logged-in user?" — meaningless without a login, so it belongs behind the gate.

The rule: routes that hand out tokens (register, login) stay open; routes that need a logged-in user go behind auth:sanctum. When M4 adds "submit a flag," that endpoint will be protected too — only real, logged-in players score.

08Checkpoint — build a protected route & close the loop

Add one protected route that reports the logged-in user, then prove the gate works from both sides. Every piece is shown above; you choose the route, attach the middleware, and test it.

You're done when

The same route returns 401 with no token and 200 + your user with a valid Bearer token — and you can explain what the auth:sanctum middleware did in between, and why /login had to stay public.

If something's off

401 even with a token? Check the header is exactly Authorization: Bearer <token> (the word Bearer, a space, then the full id|string token from login — not a truncated copy). Getting HTML or a redirect instead of JSON 401? The request isn't being treated as api/* JSON — confirm you're calling the /api/... URL. 500, not 401/200? Likely a syntax slip in the new route — read the php artisan serve terminal or php artisan route:list for the real error (the browser's CORS message is a red herring, remember).
