Async JavaScript & fetch

🎯  Goal: pull your route's JSON with fetch — from the console 🧠  Refresh: promises, async/await (rusty but load-bearing) 🧩  Concept: how JS waits without freezing
Read me first

Next lesson your Vue app will ask Laravel for data over the network. But network calls take time, and JavaScript handles "takes time" differently from the blocking code you're used to in C or Java. This is one of the JS fundamentals you flagged as rusty — so we refresh it properly now, on its own, before wiring it into a component.

No product code today. You'll practise in the browser console, and by the end you'll pull the exact JSON array you built back in M1-02 — or hit an instructive wall that sets up the lesson after this. Both are wins.

01Why "async" exists at all

In C, if you call a blocking read() on a socket, the thread stops until bytes arrive. That's fine when you have threads to spare. But JavaScript in the browser runs on a single thread — the same one that handles clicks, scrolling, and repainting. If that one thread blocked for 300 ms waiting on a server, the entire page would freeze: no clicks, no scroll, nothing. Unacceptable.

So JS never blocks on I/O. Instead, a slow operation (like a network request) returns immediately with a placeholder, the thread goes back to handling the UI, and your code runs later, when the data actually arrives. "Async" is just this idea: start now, finish later, don't freeze in between.

Bridge — from your parallel-programming background

You've met this shape before. A blocking call you'd wrap in a worker thread and hand back a future; the caller keeps going and reads the future once it's ready. JS bakes that pattern into the language — except there's only one thread and an event loop scheduling the continuations, rather than an OS thread pool. Same goal (don't stall on I/O), different machinery.

02A Promise is a value that isn't here yet

A Promise is an object standing in for a result that will exist later. It's in one of three states:

StateMeaning
pendingthe work is still in flight — no value yet
fulfilleddone; it now holds a value (e.g. the server's response)
rejectedfailed; it holds an error instead

If you've used a Future / CompletableFuture, this is that — JavaScript's spelling of a future. The old-school way to read one is .then() for the value and .catch() for the error:

js — the .then() style (illustrative) 
fetch(url)                          // returns a Promise, right away
  .then(response => response.json()) // when it resolves, do this…
  .then(data => console.log(data))   // …then this with the parsed data
  .catch(err => console.error(err)); // if anything rejected, land here

This works, but chains of .then() get awkward fast. There's a much nicer syntax on top of the exact same promises — next.

03async / await: promises that read top-to-bottom

await tells JS: "pause this function until the promise resolves, then give me its value." The result reads like ordinary sequential code — but under the hood it's the same non-blocking promise, and the browser stays free while it waits.

js — the async/await style (same work, clearer) 
async function load() {                 // 'async' marks a function that can await
  const response = await fetch(url);    // wait for the Response…
  const data = await response.json();   // …then wait for the body to parse
  console.log(data);                    // now use it, as if it were synchronous
}
KeywordWhat it does
asyncMarks a function as asynchronous. It may use await inside, and it always returns a Promise.
awaitPauses this function until the promise settles, then unwraps its value (or throws its error). Only legal inside async (and at the console's top level).
"Pauses the function" ≠ "freezes the browser"

This is the point people miss. await suspends only the async function you're in — it hands control back to the event loop, which keeps painting, handling clicks, running timers. When the promise resolves, your function resumes where it left off. It looks like blocking; it behaves like cooperative yielding. That's the whole trick.

04The fetch API — two steps, not one

fetch(url) is the browser's built-in HTTP client. The one thing to burn in: it takes two awaits, because a response arrives in two parts — first the headers/status, then the body.

1
const res = await fetch(url)
Resolves as soon as the Response headers arrive. res holds res.status (e.g. 200), res.ok, and headers — but not yet the parsed body.
2
const data = await res.json()
Reads the body to completion and parses the JSON. That's also async (the body may still be streaming in), so it returns a Promise too — hence the second await.
The famous gotcha: fetch does NOT reject on 404/500

A 404 or 500 is still "a response that arrived," so fetch considers it a success and resolves normally. It only rejects when the request couldn't be made at all (network down, DNS fail, blocked by the browser). So you check HTTP errors yourself with res.ok (true for 200–299). Forgetting this is a classic bug — you try to .json() an error page and get confused.

js — the full idiom, with error handling (illustrative) 
async function load() {
  try {
    const res = await fetch(url);
    if (!res.ok) throw new Error(`HTTP ${res.status}`); // catch 404/500 yourself
    const data = await res.json();
    console.log(data);
  } catch (err) {
    console.error('request failed:', err);              // network error OR the throw above
  }
}

Notice await lets you use a plain try/catch for async errors — the same error handling you already know, no special callback needed. And when you point this at your backend, data will be exactly the JSON array Laravel serialized from your /test-php-array route — the array-becomes-JSON rule from M1-02, now arriving in JavaScript.

06Checkpoint — pull your JSON from the console

No files to edit — this is a console experiment. The browser console allows top-level await, so you can run fetch live and watch it work (the DevTools Console is a real JS REPL). Have both servers running first.

You're done when

You can explain what fetch returns and why the idiom needs two awaits — and you've actually run the fetch in the console and recorded what came back (your JSON array, or the CORS error text). Hitting the wall counts as success here; it's a set-up, not a failure.

If you get a different error

Failed to fetch with a CORS note is the expected one. But if you see ERR_CONNECTION_REFUSED, your Laravel server isn't running (start it). If data is undefined, you likely skipped the second await. Copy the exact text and bring it — the error is the lesson.
