CORS & the /api Route

🎯  Goal: the console fetch comes back GREEN with your JSON 🔐  A core web-security mechanism — right up HTB's alley 🧩  Concept: the Same-Origin Policy & CORS opt-in
Read me first

Your evidence from last checkpoint is the whole lesson in one screenshot: Laravel answered 200 OK with Content-Type: application/json — a perfect response — yet the browser console said "blocked by CORS policy." The server said yes; the browser said no. This lesson explains that gap and closes it, the professional way.

I verified every command below against your installed Laravel 13, so they're exact for your version. By the end, that same fetch returns your { name, age, email } — the last green light before we put it on the page.

01The server said yes — the browser said no

Read your own two logs side by side. They look contradictory until you realise two different programs are talking:

Where you lookedWhat it reportedMeaning
Network tab (the server's reply) 200 OK, application/json Laravel ran your route and sent the JSON. Nothing wrong server-side.
Console (what JS is allowed to read) blocked by CORS policy, Failed to fetch The browser refused to hand that response to your JavaScript.

The request left, arrived, and was answered. Then the browser — sitting between the server and your JS — inspected the reply, saw no permission slip for the :5173 origin, and withheld the body from your code. The data physically came back; the browser just wouldn't let your script see it. The browser is the gatekeeper, not Laravel.

02Why: the Same-Origin Policy

Browsers enforce a rule called the Same-Origin Policy: by default, JavaScript may only read responses from its own origin. An "origin" is the triple scheme + host + port:

two origins — different ports = different origins 
http://localhost:5173     <-- your Vue app  (the origin of the JS making the call)
http://localhost:8000     <-- your Laravel API
     scheme   host  port

Same scheme, same host — but 5173 ≠ 8000, so to the browser these are different origins, and a call from one to the other is cross-origin. Blocked by default.

Why this rule exists (your HTB security angle)

Imagine you're logged into bank.com in one tab. You open evil.com in another. Without the Same-Origin Policy, JavaScript on evil.com could quietly fetch('https://bank.com/account') — your browser would attach your bank.com cookies automatically — and read your balance, or move money. The SOP is the wall that stops one site from reading another site's responses using your credentials. It's a foundational browser defense — the kind of mechanism you'll be probing from the other side on Hack The Box.

03CORS is how the server says "this origin is allowed"

But legitimate cross-origin calls are everywhere — including ours (our own frontend calling our own API). So there's a sanctioned way to permit them: CORS — Cross-Origin Resource Sharing. The server adds a response header naming who's allowed to read it:

the permission slip — a response header the server adds 
Access-Control-Allow-Origin: http://localhost:5173

When the browser sees that header and it matches the caller's origin, it releases the response to the JS. Your blocked response simply didn't carry this header (the console even told you: "No 'Access-Control-Allow-Origin' header is present"). CORS is strictly the target server's decision — the browser just enforces it. Note the direction: CORS loosens the Same-Origin Policy on purpose; it's a permission system, not a lock.

Bank for later: "preflight"

Your call was a plain GET with no custom headers — a "simple request" — so the browser just sent it and checked the reply. For fancier requests (a POST with a JSON content-type, custom headers, etc.) the browser first sends a tiny OPTIONS "preflight" asking permission before the real request. You'll meet preflight when we start POSTing login data in M2. Not today.

04Why your route was blocked (and the clean fix)

Here's the twist I verified in your vendor/: Laravel already ships CORS handling and it's switched on (a HandleCors middleware runs on every request). So why no header? Because its default config only applies CORS to one set of paths:

Laravel's DEFAULT cors config (what your app uses right now) 
'paths' => ['api/*', 'sanctum/csrf-cookie'],   // CORS only applied to these
'allowed_origins' => ['*'],                    // ...and there, ANY origin is allowed

Your route is /test-php-array — a web route, which does not match api/*. So HandleCors looked at it, saw it wasn't a CORS-managed path, and added no headers. The fix follows directly: put your data endpoint where the API belongs — under /api. The moment it matches api/*, the default config (allowed_origins: ['*']) applies and the browser is satisfied.

Bonus you already spotted: the session cookies vanish

Remember those Set-Cookie: XSRF-TOKEN / laravel-session headers on your response? Those come from the web middleware group (it manages sessions). The api group is stateless — no session middleware — so once your route lives under /api, it stops emitting those cookies. That's exactly what you want for an API: every request stands alone. Moving to /api fixes CORS and makes the endpoint behave like a proper API.

05The fix, in two beats

Beat 1 — move the route under /api (this alone turns the light green). Beat 2 — tighten who's allowed (the professional, security-minded follow-up). I'll describe each; you write the edits.

Beat 1 — give your app API routing

Right now you have no routes/api.php. Create one, then tell Laravel about it. Your bootstrap/app.php already registers the web routes — you're adding a sibling for the API:

builder/backend/bootstrap/app.php — you add ONE line 
->withRouting(
    web: __DIR__.'/../routes/web.php',
    // ← add an  api:  line here, mirroring the web: one above,
    //   pointing at your new routes/api.php
    commands: __DIR__.'/../routes/console.php',
    health: '/up',
)

Then move your existing /test-php-array handler out of web.php and into api.php (same handler you already wrote — just relocate it). The api group auto-prefixes routes with /api, so its real URL becomes /api/test-php-array. Confirm with:

verify the route exists where you expect 
php artisan route:list --path=api
# you should see:  GET|HEAD   api/test-php-array
Don't run php artisan install:api for this

It's the "official" way to add API routing, but it also installs Laravel Sanctum, publishes an auth migration, and interactively asks to run migrations — that's login-token scaffolding for M2, not now. Adding the one api: line yourself is cleaner and keeps today focused.

Now update your console fetch to the new URL — http://localhost:8000/api/test-php-array — and re-run it. It should come back green: your JSON, no CORS error, no Set-Cookie. That's the round-trip's data path, open at last.

Beat 2 — stop allowing every origin

It works now because the default allowed_origins is ['*'] — any website may call your API from a browser. Fine in dev, sloppy for a real product. Lock it to your frontend. First publish the config so you can edit it:

publish the CORS config into config/cors.php 
php artisan config:publish cors

Then in the new config/cors.php, change allowed_origins from the wildcard to your exact origin:

config/cors.php — one value changes 
'allowed_origins' => ['http://localhost:5173'],   // was ['*']
Three gotchas that waste an afternoon

1. It's an origin, not a URL. http://localhost:5173 exactly — no trailing slash, exact port. A mismatch fails silently (still blocked).
2. If edits seem ignored, run php artisan optimize:clear. You don't need to restart artisan serve (it reboots each request), but a stale config/route cache would override your changes.
3. Don't reach for credentials. Leave supports_credentials as false and keep the fetch a plain GET. Turning on credentials with allowed_origins: ['*'] is actually forbidden by the CORS spec — that's a cookie-auth topic for M2, with a specific origin.

Why not the "easy" Vite proxy?

You may read that you can dodge CORS with a Vite dev-server proxy. It works — but only in npm run dev; it evaporates on npm run build, and in production your Vue app and API really are separate origins. Configuring CORS properly is the skill that survives to deployment (M5). We do the real thing.
