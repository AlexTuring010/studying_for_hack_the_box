M1 · Plumbing Concept 4

Standing Up Vue

🎯  Goal: a second app — the frontend — running in your browser 🌉  Bridge: the JS toolchain is Composer all over again 🧩  Concept: two apps, two servers, two ports
Read me first

You have a backend that returns JSON — but nobody's using that JSON yet. A backend with no frontend is a kitchen with no dining room: the food's being cooked, there's just no room to serve it. This lesson builds the dining room — the Vue app that will (next lesson) fetch your route's data and show it to a human.

Today's job is narrow on purpose: just get Vue running in the browser, side by side with Laravel. The two talking to each other is the very next lesson — and the moment Milestone 1 is complete.

01Two apps, not one

Back in M1-02 you learned the plan: Laravel emits data (JSON), the browser assembles the page. That sentence has a big consequence we can now make real — your project is two separate applications, each with its own job, its own folder, and its own running server:

Bridge — from your React/Next dabbling (light)

If your hackathon Next.js app rings a faint bell — same family. A Vue app is a Single-Page Application: the browser downloads a JS bundle once, and that JS draws and re-draws the UI, calling an API for data as needed. We're just running the API (Laravel) and the SPA (Vue) as two separate projects instead of one combined Next app, because Hack The Box's real stack keeps them apart. If the Next comparison doesn't help, ignore it — the table above is all you need.

Here's the gift: the JavaScript toolchain is the same shape as the PHP one you met two lessons ago. Every piece has a twin you already understand:

The one that matters most: node_modules/ = vendor/

Everything you learned in M1-03 about vendor/ applies verbatim to node_modules/: it's thousands of files you didn't write, rebuilt on demand from the lock file, and it must never be committed. Your root .gitignore already lists node_modules/ — so you're protected before you even create it. We'll confirm that at the checkpoint.

The one genuinely new name is Vite (say "veet"). It's the frontend's dev server and bundler — the thing npm run dev actually starts. Think of it as php artisan serve's more powerful cousin: it serves your app on a local port and gives you hot reload — edit a file, and the browser updates instantly without a manual refresh.

Good news: Node is already installed

Unlike Laravel in M1-01, you don't have a big install to do — this machine already has Node v22 and npm. You'll just verify that at the checkpoint (node --version). If it were ever missing, the fix is one download from nodejs.org (the "LTS" build) — but you won't need it today.

03Create the app and run it

Just as laravel new scaffolded your backend, one command scaffolds a Vue app. Run it from inside builder/ so the new project lands next to backend/. The general shape:

the scaffold command — run it INSIDE builder/ 
npm create vue@latest        # the official Vue scaffolder; it asks a few questions
# ...then...
cd frontend                  # into the app it just made
npm install                  # download dependencies → creates node_modules/
npm run dev                  # start Vite; open the http://localhost:5173 it prints

npm create vue@latest asks you a short list of yes/no questions (project name, TypeScript?, Router?, Pinia?, testing?…). For this milestone, keep the surface small — name it frontend and answer No to the optional add-ons. You want the smallest thing that renders.

Why say "no" to Router and Pinia for now

You'll hear that "real" Vue apps use Vue Router (page navigation) and Pinia (shared state) — and ours will too. But a professional adds a tool when the problem it solves shows up, not before. Router earns its place when we have multiple pages (M3); Pinia when we have login state to hold (M2). Adding them now would be three unfamiliar things at once with nothing to do. We'll bring each in deliberately, at the milestone that needs it.

After npm run dev, opening http://localhost:5173 shows Vue's starter welcome page — the frontend's equivalent of Laravel's welcome page. It's a scaffold you'll gut and replace, exactly like you will with welcome.blade.php. Seeing it means your frontend is alive.

04Running both servers at once

This is the mental model to lock in. To build the round-trip next lesson, you'll have two dev servers running simultaneously, in two separate terminals:

A
Terminal 1 — the backend
In builder/backend/: php artisan serve → your Laravel API on http://localhost:8000. This terminal is now "busy" holding that server (remember M1-01).
B
Terminal 2 — the frontend
In builder/frontend/: npm run dev → your Vue app on http://localhost:5173. A second busy terminal, a second process.

They are two independent programs on two ports. Right now they don't know the other exists — visiting :5173 shows Vue, visiting :8000 shows Laravel, and neither calls the other. Next lesson we make the Vue app reach across to :8000 and fetch your route — and meet the browser's cross-origin safety rule (CORS) that guards exactly that kind of call. For today: just prove both can run at the same time.

05A 30-second orientation: what's a .vue file?

So the scaffold isn't a black box — a quick map, no deep dive (you'll actually edit one next lesson). Vue apps are built from components, and each lives in a .vue "single-file component" that bundles three labelled parts:

the shape of a .vue file — orientation only, not your task 
<script setup>   // the JavaScript: data and logic for this component
</script>

<template>       // the HTML: what this component draws
</template>

<style>          // the CSS: how it looks (optional)
</style>

The root component is App.vue, mounted onto the page by src/main.js. If you've touched React: a .vue file is one component, like a React component — except instead of JSX mixing markup into JS, Vue keeps markup, logic, and style in three clearly separated blocks. That's all you need to hold today; we open one for real next time.

If a command errors

npm errors are wordy but usually specific. Copy the exact output — especially the first red npm ERR! line and the command you ran — and bring it to me. "It didn't work" is hard to debug; the error text is easy. A port already in use, a wrong folder, or a typo'd command are the usual suspects.
